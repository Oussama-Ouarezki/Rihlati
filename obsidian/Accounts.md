| — | Sahara Évasion (Ghardaïa) | *(no members)* | Left **pending** so `/admin/` has a verification queue |

Password for both: **`preview-password`**.

> [!info] Why a plaintext password is fine in a note and in the seed file
> It grants access to fake agencies in a scratch SQLite file that is regenerated by one
> command, and it appears nowhere else. That is the whole test: a secret is a secret because
> of what it unlocks, not because of what it looks like. Rule 1 in [[The Seven Rules]] is
> about credentials that reach production — a `.env` value, an API key, a real signing key.
> Those never appear in this vault or in a commit.
>
> The seed file marks it explicitly: `PASSWORD = "preview-password"  # throwaway local
> fixture, not a credential`. Say so in the code, so nobody has to guess.

> [!warning] Never seed a real agency or a real phone number
> A development database gets copied around — onto a laptop, into a bug report, into a
> screenshot. A copy is a leak. Every seeded traveler is `Traveler One`, `+213555000001`, and
> so on, for exactly this reason.

## Logging in

By **username**, not email. Django's `AbstractUser` uses `username` as the login field and
this build did not change that.

```bash
curl -s -X POST localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"amina","password":"preview-password"}'
```

You get back an access token (15 minutes) and a refresh token (30 days). See [[Auth Flow]]
for why there are two and what happens when one is stolen.

> [!info] Django vs NestJS
> The NestJS repo logs in with an `identifier` field that accepts an email *or* a phone
> number, and its seeded accounts are `baraka@rihlati.test` and friends. Here it is a plain
> username. That is a real gap, not a design choice: agencies in Algeria are far more likely
> to remember a phone number than an email, and neither repo should be asking for a
> username. See [[Milestone Plan]].

## Rihlati staff, and how someone becomes one

There is no "platform admin" column. Staff status is Django's own **`User.is_staff`**, and
`require_staff()` in `apps/accounts/api.py` reads it **from the database on every request** —
never from a token claim. That matters: revoking someone's staff access bites immediately
instead of waiting up to fifteen minutes for their access token to expire. See
[[Authentication vs Authorization]] for why a token is the wrong place to keep a permission.

Granting it is not an endpoint. It is a command:

```bash
.venv/bin/python manage.py createsuperuser          # the first one
.venv/bin/python manage.py shell                     # promote an existing account
```

```python
from apps.accounts.models import User
u = User.objects.get(username="someone"); u.is_staff = True; u.save()
```

**Why a shell and not a page.** Chicken and egg: an endpoint that promotes someone to staff
would itself have to be protected by staff, so the *first* one could never be created through
it. Something outside the API has to bootstrap it.

The obvious alternative — an endpoint that works only while zero staff exist — is worse. It is
a public "make me god" route that is armed on every fresh deployment, and a race between
deploying and registering hands the platform to whoever wins it. Moving the boundary to the
shell moves it to something an attacker on the internet does not have: server access and the
database credentials. If they already have those, this is not what you lost.

### What staff can see

Four endpoints, and they are the **only** cross-tenant surface in the entire API:

| Endpoint | What it exposes |
|---|---|
| `GET /api/admin/verification-queue` | every pending agency, oldest first |
| `POST /api/admin/agencies/{id}/decision` | grants or refuses the badge |
| `POST /api/admin/agencies/{id}/suspend` | takes it away |
| `GET /api/admin/reconcile-ratings` | recomputes the denormalised rating counters |

Everything else in the app is scoped by `agency_id` (see [[Multi-Tenancy]]). These four are
not, because Rihlati staff review agencies they are by definition not members of. So ask
yourself what is left protecting the data once the scoping is gone — and the honest answer is
**one boolean**. That is why `require_staff` is three lines with a comment on it, and why
those routes deserve more scrutiny per line than anything else here.

An agency's `registre_commerce`, `nif`, `tourism_licence` and the owner's phone number are all
reachable through that queue. Grant `is_staff` the way you would hand over a key, not the way
you would tick a checkbox. See [[Agency Verification]].

## Open questions

- **Should promoting a user to staff write an audit row?** It doesn't today, because it
  happens in a shell where there is no `request` and therefore no honest `actor` to record.
  The NestJS repo writes one with a null actor and a comment admitting the script doesn't
  know who was at the keyboard. That's arguably better than no row at all — your call.
- **Should staff decisions be visible to the agency they're about?** `Agency.decision_note`
  is internal and `rejection_reason` is shown verbatim to the owner. Whether the *reviewer's
  name* should be visible too is a policy decision, not a technical one.
